# T08 반복 계산과 호출 한도 소진

GPT-4o mini Planner-only 1회 실험에서 T08은 검색에 성공했지만, 하루 나트륨 상한을 초과하는 조합의 계산을 반복했다. Planner는 최종 식단 JSON을 제출하지 않은 채 라운드당 호출 한도를 3회 소진했고, 식단 미반환으로 종료됐다.

실행 기록은 `artifacts/ablation/4o-mini/planner-only-r1-20261106-220204-961196`에 저장되어 있다. 아래 중간 계산 식단과 사후 구성 예시는 실제 최종 반환 식단과 구분한다. 사후 평가를 Planner에 피드백하거나 추가 모델 실행을 하지는 않았다.

## 사용자 요청과 실행 결과

> 평소 외식을 자주 해서 나트륨 섭취량을 줄이려고 해. 이틀 동안 점심과 저녁을 추천해 줘. 하루에 먹는 두 끼의 나트륨 합계는 1,600mg 이하여야 하고, 각 끼니는 350~750kcal여야 해. 전체 45,000원 이하, 한 끼 15,000원 이하로 해줘.

| 항목 | 기록 |
|---|---|
| 모델과 모드 | `gpt-4o-mini`, `planner_only` |
| 반환 상태 | `not_verified` |
| 종료 원인 | `call_limit` |
| 모델 호출 수 | 18회 |
| 도구 실행 수 | `search_foods` 1회, `compute_plan` 17회 |
| 라운드 수 | 3회 |
| 실제 반환 식단 | 없음 |
| 턴 소요 시간 | 약 56.12초 |

## 검색과 자체 수정 과정

첫 검색은 열량 350~750kcal, 음식별 나트륨 1,600mg 이하, 가격 15,000원 이하를 적용했고 16개 음식을 반환했다. 검색의 `sodium_max`는 음식별 필터다. 사용자가 요구한 하루 두 끼의 합계 상한은 `compute_plan`의 일별 결과를 보고 따로 맞춰야 한다.

첫 `compute_plan` 실행의 하루 나트륨은 1일차 1,654mg, 2일차 1,884.6mg으로 모두 상한을 초과했다. 이후 Planner는 음식 배치를 바꾸며 계산을 이어갔지만, 후반에는 아래 같은 조합을 총 11번 계산했다.

```json
{
  "plan": {
    "day1_lunch": ["F008"],
    "day1_dinner": ["F046"],
    "day2_lunch": ["F020"],
    "day2_dinner": ["F045"]
  }
}
```

이 식단은 `compute_plan` 인자로만 등장한 중간 계산 대상이다.

| 날짜 | 점심과 저녁 | 계산된 하루 나트륨 | 요구 상한 | 사후 판정 |
|---|---|---:|---:|---|
| 1일차 | 콩나물국밥 F008 + 와퍼버거 F046 | 1,272.98mg | 1,600mg | 충족 |
| 2일차 | 제육볶음 F020 + 통새우버거 F045 | 1,904.6mg | 1,600mg | 304.6mg 초과 |

이 조합의 총가격은 31,900원이고 각 끼니 열량·가격은 요구 범위 안에 있다. `metric.evaluate_plan`으로 중간 식단을 사후 진단하면 `sodium_per_day`가 실패한다.

이틀 나트륨 합계는 3,177.58mg이지만 요청은 **각 날짜마다 1,600mg 이하**다. 이틀 합계만 3,200mg 이하인 것으로는 충분하지 않다. 다만 모델이 실제로 이틀 합계와 하루 상한을 혼동했는지는 저장 기록만으로 확정할 수 없다.

## 호출 한도에서 종료된 과정

| 라운드 | 실행한 도구 | 모델 호출 수 | 라운드 종료 |
|---|---|---:|---|
| 1 | 검색 1회, 계산 5회 | 6회 | 라운드당 호출 한도 도달 |
| 2 | 계산 6회 | 6회 | 라운드당 호출 한도 도달 |
| 3 | 계산 6회 | 6회 | 라운드당 호출 한도 도달 |

실제 설정은 `max_agent_calls=6`, `max_rounds=3`, `max_turn_calls=24`였다. 각 라운드에서 마지막 허용 호출까지 도구 호출을 선택해 최종 응답을 제출할 기회를 사용하지 못했다. 매 라운드 후 `planner exceeded per-agent model call limit`이라는 기술적 피드백이 전달됐지만 반복 계산이 이어졌다.

총 18번의 모델 호출 뒤 3개 라운드를 소진했으며, 직접적인 종료 원인은 라운드당 호출 한도였다. API 오류나 비용 한도 초과는 기록되지 않았다.

## 사후 확인한 실행 가능성과 평가 해석

검색 결과에 있던 콩나물국밥 F008과 잡채밥 F023을 매일 한 끼씩 배치하는 예시는 다음 수치를 가진다.

| 항목 | 사후 구성 예시의 수치 | 요구 범위 |
|---|---:|---|
| 하루 나트륨 | 894mg | 1,600mg 이하 |
| 끼니별 열량 | 480kcal, 510kcal | 각각 350~750kcal |
| 끼니별 가격 | 8,500원, 9,500원 | 각각 15,000원 이하 |
| 이틀 총가격 | 36,000원 | 45,000원 이하 |

사용자 요청에는 음식 중복 금지 조건이 없다. 위 예시는 `metric.evaluate_plan`의 모든 항목을 사후 통과했으며 실제 모델이 제출한 식단은 아니다.

관찰된 실패는 **제약을 만족하는 조합으로 전환하지 못한 반복 계산과 최종 후보 미제출**이다. 실제 독립 평가 대상 출력은 미반환이므로 요구 슬롯 누락으로 실패한다. 중간 식단의 나트륨 위반은 진단 근거로만 사용하며, 이를 사용자에게 잘못된 식단을 반환한 사례로 집계하지 않는다. 이번 실행에는 Verifier가 없으므로 Verifier의 수정·차단 효과도 판정할 수 없다.
